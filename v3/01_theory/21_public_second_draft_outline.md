構造持続理論: 推定レイヤーと検証規律
— 観測指標、凍結検証、支持・非支持・沈黙 —

status: public_second_draft_outline

本メモは、公開第二稿の章立て候補である。新しい支持判定、実験結果、理論主張を追加するものではない。公開第一稿「構造持続理論: 基礎と仕様固定アンカー」が、基礎座標と仕様固定レイヤーを扱うのに対して、本稿候補は、直接 \(V,m\) を数えられない系で観測・推定指標をどう扱うかを主題にする。


1. 本稿の位置づけ

公開第一稿では、維持条件 \(G\)、維持可能領域 \(V\)、ものさし \(m\)、構造消耗 \(L\)、回復込み純消耗 \(B\)、資源側の有効維持余力 \(M\) を導入した。さらに、有限 CSP、二元消失通信路上の線形符号、有限グラフのように、仕様から \(V,m\) と判定境界を固定できる場合には、操作的アンカーが得られることを示した。

公開第二稿では、その前提を受けて、仕様から \(V,m\) を直接数えられない現実系を扱う。ここでは \(L\) や \(B\) は直接観測される量ではない。矛盾密度、依存関係の破断、契約整合性、性能劣化、故障率、保持率などの観測・推定指標を、構造座標の候補読出しとして凍結し、未使用データで検証する。

この稿の中心は、推定指標を理論座標そのものと混同しないことである。推定レイヤーで得られる支持は、仕様固定レイヤーの定理や厳密会計とは異なる強度を持つ。


2. なぜ推定レイヤーが必要か

多くの現実系では、維持可能領域 \(V\) とものさし \(m\) を直接固定できない。

例:

- 長い推論過程では、整合的に完答できる推論経路の集合を直接数えられない。
- 継続学習では、更新後も依存知識が整合した内部状態の集合を直接数えられない。
- ソフトウェア開発・保守では、安全に変更・復帰できる経路集合を直接数えられない。
- 事業、組織、制度では、当該機能を担う有効状態・行動・経路の集合を直接数えられない。

したがって推定レイヤーでは、\(V,m\) の代わりに観測・推定指標を置く。ただし、その指標は \(L\) や \(B\) そのものではなく、凍結された写像のもとでのみ候補読出しとして扱う。


3. 構造座標・資源側量と観測指標を分ける

第一稿で導入した主な維持可能領域側の座標は、次の対象である。

\[
  L,\quad B,\quad d_t,\quad r_t,\quad b_t.
\]

これとは別に、\(M\) は資源側の有効維持余力として置く。推定レイヤーで実際に観測されるのは、これらの座標・量そのものではなく、たとえば次のような指標である。

| 系 | 候補指標 | 読み |
|---|---|---|
| 大規模言語モデル (LLM) 推論 | 矛盾密度、参照衝突、整合完答率 | 推論経路の縮退候補 |
| 継続学習 | 旧知識保持率、依存整合率、更新後の破断数 | 知識構造の再編失敗候補 |
| ソフトウェア | 契約違反、依存破断、変更失敗率、復帰不能パス | 保守可能領域の縮小候補 |
| 事業・組織 | 意思決定遅延、承認経路破断、代替経路数 | 機能維持経路の縮小候補 |
| 機械・運用系 | 故障率、復旧時間、冗長性消失、サービス水準違反 | 維持余力または維持可能領域の候補読出し |

同じ観測値でも、どの維持条件 \(G\) を読むのか、また資源側の \(M\) を読むのか維持可能領域側の \(L/B\) を読むのかによって意味が変わる。したがって、推定指標は観測後に選び直してはいけない。どちらの側を読むかは凍結時に固定する。


4. 凍結検証の基本手順

推定レイヤーで支持を主張するには、結果を見る前に次を固定する。

1. 対象ドメインと維持条件 \(G\)
2. 予測または判定したい終点
3. 観測・推定指標
4. 比較する基準モデル
5. 評価量
6. データ分割
7. 支持判定規則
8. 失敗時の記録形式

この手順を凍結検証と呼ぶ。凍結検証は、良い結果を得るための儀式ではない。観測後の指標選択、基準モデルの差し替え、評価量の選び直し、失敗した実行の救済を防ぐための規律である。


5. 支持・非支持・沈黙

推定レイヤーでは、結果を少なくとも三つに分ける。

| 判定 | 意味 |
|---|---|
| 支持 | 凍結された主判定規則を未使用データで通過した |
| 非支持 | 凍結された主判定規則を評価できたが、通過しなかった |
| 沈黙 | 観測可能性、データ品質、ラベル定義、比較可能性が足りず、支持判定を行えない |

無効実行は非支持とは異なる。生成面や代数面、ラベル面が凍結前提を満たさず、主判定規則そのものが評価できなかった場合は、非支持ではなく無効実行として記録する。

重要なのは、非支持を失敗として消さないことである。非支持は、その写像、指標、終点、基準モデルの組み合わせでは支持が取れなかったという情報であり、次の設計を狭める。


6. 失敗台帳の役割

失敗台帳は、理論を弱く見せるためではなく、理論を空虚にしないために必要である。

主な規律:

- 失敗した凍結検証を、同じデータ集合のまま支持へ改名しない。
- 非支持の実行を、後から別の評価量で救済しない。
- 無効実行を非支持と混同しない。
- 後続実行は新しい設計、明示された新しい固定仕様書、別の記録として扱う。
- 厳密アンカーと予測支持を混同しない。

この規律により、推定レイヤーは「当たった事例だけを集める」形式から離れられる。


7. 代表的な設計教訓

現時点の失敗台帳から、少なくとも次の教訓が得られている。

1. 厳密会計アンカーは、そのまま予測支持ではない。
   全域木数のような大域的冗長性は厳密会計として強くても、短期切断確率の主予測量としては局所 cutset とずれる場合がある。

2. 生成面の実現可能性は、凍結前に確認する。
   符号生成やグラフ生成では、代数的制約や生成制約により、予定したセルが実現不能になることがある。

3. 弱い基準モデルに勝っても十分ではない。
   より自然なドメイン事前分布、ドメイン既知量、強い基準モデルに勝てなければ、主支持とは呼ばない。

4. 順位信号と確率予測支持は異なる。
   ランキングが良くても、凍結された対数損失や較正評価で通らない場合がある。

5. 方向が正でも、主判定基準未満なら非支持である。
   改善が小さい場合、それを「弱い支持」と呼ぶのではなく、事前に定めた判定規則に従う。


8. 候補ドメイン

本稿では、以下のような推定レイヤー候補を扱う。

1. 大規模言語モデル (LLM) 推論劣化
   長文脈、矛盾注入、参照衝突、未整理更新により、整合的な完答経路が縮退するかを観測する。

2. 継続学習と構造的忘却
   単なる旧タスク精度ではなく、依存知識の再編と保持の失敗を観測する。

3. ソフトウェア開発・保守
   仕様、実装、依存関係、契約の整合性が崩れ、安全に変更・復帰できる経路が縮むかを見る。

4. 現実運用・信頼性ドメイン
   故障、復旧、予備力、サービス水準違反、較正損失などを、構造持続座標の候補読出しとして扱う。

5. 事業・組織・制度
   意思決定、承認、代替経路、制度的正統性などを扱うが、測度の恣意性が大きいため、原則として探索候補または沈黙候補として慎重に扱う。
   企業については、価値提供、資源獲得、能力再生産、環境適応の循環を維持する系として読む作業仮説を置く。利益がまだ出ていないスタートアップでも、価値仮説から得た学習、信用、資金、採用力を次の価値生成能力へ変換できるかを候補指標にできる。ただし、これは支持済み指標ではなく、固定された未来シナリオ集合と探索手続きの下で、発見された対応策から実行可能な対応策への縮小を見る候補である。


9. 第二稿で主張すること、しないこと

本稿は、次を主張する。

1. 直接 \(V,m\) を数えられない系では、観測・推定指標を候補読出しとして凍結する必要がある。
2. 推定レイヤーの支持は、仕様固定レイヤーの定理や厳密会計と異なる証拠強度を持つ。
3. 支持、非支持、沈黙、無効実行を分けることで、理論の空虚化を防げる。
4. 失敗台帳は、否定的結果を保存し、次の設計を狭めるための方法論的部品である。

本稿は、次を主張しない。

1. 推定指標が \(L\) や \(B\) そのものであること。
2. 大規模言語モデル、継続学習、ソフトウェア、組織に一つの普遍的指標があること。
3. 仕様固定レイヤーの操作的アンカーが、そのまま現実ドメインでの予測勝利になること。
4. 非支持を後から解釈し直せば支持になること。
5. 沈黙を理論的成功または失敗として読むこと。
